## What Was Done This Session

The session had two main threads.

**Thread 1 — Finishing the Shiprocket webhook (carried over from the previous session).**
The previous session had built the Shiprocket webhook at `/api/delivery/status` but it wasn't updating orders correctly. The root cause was discovered: the AWB (Air Waybill / tracking number) is only assigned in Shiprocket *after* an admin manually clicks "Ship Now" and selects a courier — it doesn't come back at order creation time. So our `tracking_id` field in the DB was an empty string, and the webhook's primary lookup (`WHERE tracking_id = AWB`) always missed. The fix was to add two fallback matching strategies: first try `shiprocket_shipment_id`, then try `shiprocket_order_id`. Both fallbacks also save the AWB back to the DB the moment they find the order, so all subsequent webhook events (out_for_delivery, delivered) will match on the first (fastest) path. The specific order MAA-20260511-0005 (Yashwanth Moparthi, Bangalore) was manually corrected in the DB — status set to "shipped", AWB `19041925135244`, courier "Delhivery Surface". This is committed at `b057e38`.

**Thread 2 — COD payment status control.**
A screenshot showed the Payment Summary card on an admin order page: Payment Method = COD, Payment Status = Pending, but no way to change it. For COD orders, the payment genuinely is pending until the delivery agent collects cash — so the "Pending" status is correct. But the admin had no way to mark it as collected. A "💵 Mark Payment Collected" button was added to the Payment Summary card. It only appears when `payment_method === "cod"` and `payment_status !== "paid"` — once tapped it disappears. Under the hood it calls the existing PATCH endpoint with `{ paymentStatus: "paid" }`, which was already supported by the API. This is committed at `74794f2`.

## Critical Context (Do NOT Skip)

1. **Prices are in paise.** ₹399 is stored as `39900`. Every price column in the DB is paise. Always multiply by 100 when writing to DB, divide by 100 when displaying.

2. **Shiprocket webhook URL is `/api/delivery/status`.** It cannot be `/api/shiprocket/webhook` or anything containing "shiprocket", "sr", or "kr". Shiprocket's own system rejects those. Do NOT rename this endpoint.

3. **AWB comes later, not at order creation.** When `pushOrderToShiprocket()` runs, it gets back a `shiprocket_order_id` and `shiprocket_shipment_id`, but the AWB/tracking number is `null`. The AWB is only assigned when the admin goes to Shiprocket dashboard and clicks "Ship Now". The webhook handles this via fallback matching — it saves the AWB back to the DB the first time it matches via `shiprocket_shipment_id`.

4. **Admin auth is completely separate from customer auth.** Customers log in via Supabase OTP (magic link to phone). Admins log in via email + bcrypt password, get a JWT in an httpOnly cookie called `mf-admin-token`, signed with `ADMIN_JWT_SECRET`. The admin_users table has DB-backed brute-force lockout (5 failed attempts = 15 min lockout). Recovery: reset `failed_login_count` and `locked_until` in Supabase dashboard.

5. **Supabase view `orders_summary`** is what all admin order list/detail APIs query — not the raw `orders` table. If you add columns to `orders`, they won't appear in admin until the view is updated too.

6. **No compare_at_price anywhere.** The launch offer code was fully removed from both the DB (via migration script) and the API layer. If you see compare_at_price anywhere in old code, it's dead code — do not re-enable it.

7. **COD payment_status = "pending" at order creation** is intentional and correct. Cash hasn't been collected yet. Admin marks it "paid" after receiving cash using the new button in the Payment Summary card.

8. **CallMeBot WhatsApp alerts to admin** are optional — only fire if `ADMIN_WHATSAPP_NUMBER` and `CALLMEBOT_API_KEY` env vars are set. They're in `cashfree-webhook/route.ts`, not in the general notification system.

## Decisions Made This Session (and Why)

**COD payment button uses existing PATCH endpoint** → The `/api/admin/orders/[orderId]` PATCH already accepted `paymentStatus` in the body. No new API route needed — just a UI addition. This keeps the code DRY and consistent with how all other order updates work (status, tracking, etc.).

**Button hides after marking paid** → State update is local (`setData` optimistic update on success). Button condition is `payment_method === "cod" && payment_status !== "paid"`. Once paid, there's no reason to show it again — cleaner UX than a disabled state.

**Shiprocket AWB fallback saves to DB immediately** → When the webhook finds an order via `shiprocket_shipment_id` fallback (because AWB wasn't in DB yet), it immediately writes the AWB to `tracking_id` in DB. This means the very next webhook event (out_for_delivery, delivered) will match on the fast primary AWB lookup — no need for fallback again. One DB write pays for itself many times over.
